## 过程说明

**本轮脚本修正 3 处**（均为脚本对旧实现的假设，不是产品缺陷）：

1. 模块 8 与越权用例原调用 `/api/dispatch/candidates/{id}`，该接口已在本轮精简中删除，改为 `/api/dispatch/assign-candidates/{id}`；
2. 建单类型从「取第一个类型（水电）」改为指定「门禁系统」——水电有李、钱两位师傅竞争，在 57 条数据的负荷下可能派给钱师傅，导致后续用 lisi 接单全挂；门禁只有李师傅会修，结果确定；
3. 改派用例补 `force: true`，因为王师傅没有门禁技能，现在会被技能校验拦住（正好验证了强制派单通道）。

**历史上的一轮问题**（保留记录）：第一轮 89 例中 4 例"失败"，经排查为脚本沿用 V1.0 假设（提交即待派单、已派单可撤销），V2.0 自动派单上线后行为已变，脚本修正后通过。

**测试副产物**：测试期间超时定时任务真实触发了一次自动改派（某条演示单派单时间超过 48 小时），改派日志与工单归属已手动复原，说明定时任务在真实时间跨度下可正常工作。

## 遗留建议（非阻断）

1. 后端仍无 `src/test` 与 `spring-boot-starter-test`，建议补充单元测试层（目前只有 API 级 E2E）。
2. 本套 E2E 可接入 CI（`python tests/e2e_api_test.py`，退出码非 0 即失败）。
3. **未覆盖**：文件上传接口、站内消息接口（含本轮新增的删除单条/清空已读）、定时催办任务（需构造时间维度）、前端 UI 层。消息模块建议手工验证一遍。
4. 演示数据有"时效"：处理中的工单超过 48 小时会被自动改派、待验收超 72 小时会收到催办消息。**答辩或截图当天请重跑一次 `sql/demo_data.sql`**，让时间回到"刚刚发生"。

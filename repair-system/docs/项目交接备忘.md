### 4.3 工单状态模型（现状，勿擅改编码）

```java
STATUS_PENDING_DISPATCH   = 0  // 待派单
STATUS_PROCESSING         = 1  // 处理中（已派单未接单 与 维修中 混用，是当前主要痛点）
STATUS_PENDING_ACCEPTANCE = 2  // 待验收
STATUS_COMPLETED          = 3  // 已完成
STATUS_CLOSED             = 4  // 已关闭
```

流转日志动作：`SUBMIT / ASSIGN / AUTO_ASSIGN / REASSIGN / ACCEPT / REFUSE / FINISH / PASS / REJECT / CANCEL / CLOSE / URGE`

> `REJECT` 专指住户验收不通过；维修工拒单是 `REFUSE`，两者不要混用。
> 状态 1 的用户感知已拆为「待接单（`workerAcceptTime` 为空）/ 维修中（非空）」，但**编码未变**，统计口径仍按 5 态计数。

## 6.1 派单规则（2026-10-28 简化重做，按用户反馈）

> 2026-10-25 首版定了 5 个条件（含"类型级开关""候选下限"），用户实测后反馈**看不懂、不会操作**，已于 2026-10-28 简化重做：判定条件砍到 3 条，`repair_type.auto_dispatch` 与 `dispatch_rule.min_candidates` 两列已删除，"电梯故障默认人工"的设定一并取消（现所有类型都可自动派）。

### A. 自动派单：3 个条件**全部满足**才触发

| # | 条件 | 数据来源 | 不满足时 |
|---|---|---|---|
| 1 | 自动派单开关 = 开（派单规则页） | `dispatch_rule.auto_dispatch_enabled` | 转人工 |
| 2 | 存在技能匹配且在岗的维修工 | `worker_skill` + `user.status` | 转人工 |
| 3 | 至少一人未满负荷（未完成单数 < `max_load`） | 实时统计（处理中+待验收） | 转人工 |

满足后按既有公式打分取 Top1：`负荷×w_load`（紧急单 `× (1+urgency_boost)`）+ `历史评分×w_rating` + `楼栋熟悉度×w_familiarity`。

### B. 转人工时系统做什么（不再静默）

1. 工单时间轴写入 `HOLD` 节点：「转人工派单：<原因>」（详情弹窗中为灰色节点）；
2. 给全部在岗管理员发站内消息：「工单【单号】未自动派单(<原因>)，请人工派单」；
3. 提交报修接口把原因返回前端，住户侧 toast 显示「本次转人工派单：<原因>」。

### C. 需要管理员手动派单的场景（只剩 4 种）

- 总开关关闭（全部工单人工派）；
- 无技能匹配的师傅 / 技能师傅全部被禁用；
- 技能匹配的师傅全部满负荷；
- 维修工拒单后工单退回待派单——**不自动重派**，由管理员决定派给谁。

### D. 类型 × 技能现状（`upgrade_v31_dispatch.sql` 已应用）

| 报修类型 | 可接单师傅 |
|---|---|
| 水电维修 | 李师傅 |
| 门窗维修 | 王师傅 |
| 电梯故障 | 王师傅 |
| 门禁系统 | 李师傅 |
| 公共照明 | 李师傅 |
| 其他 | 王师傅 |
| **网络故障** | **周师傅（仅此一项技能）** |
| 水电维修 / 门窗维修（重复行） | **钱师傅**（水电+门窗，与李/王师傅重叠） |

> 按当前用户数据，**7 个类型每个都有在岗技能师傅，正常情况下所有新工单都会自动派**。水电、门窗各有两位候选，自动派单的打分与负荷均衡逻辑真实生效；其余类型仍是单一候选（"指名派"）。演示"转人工"的方法：禁用某类型唯一的师傅（如周师傅），再提交该类型工单。

### E. 超时自动改派

- 处理中超过 `reassign_hours`（48h）→ 排除"已试过的人"和"满负荷的人"后改派次优，最多 `reassign_limit`（2）次，超限通知管理员。

### F. 配置入口（改完即时生效）

| 入口 | 路径 | 可改内容 |
|---|---|---|
| 派单规则（菜单） | `/dispatch-rule` | 自动派单开关、负荷上限；权重/改派等高级参数收在折叠面板，保持默认即可。页面附「师傅技能一览」矩阵（谁会修什么一目了然） |

## 6.5 本地辅助填写（2026-10-28，第四轮，替代 AI）

不用大模型，纯前端词库解决"不知道该怎么写"。**不联网、不调接口、断网可用、零成本、响应即时**。

| 项目 | 内容 |
|---|---|
| 新增文件 | `frontend/src/utils/suggest.js`（唯一新增，约 300 行文案 + 3 个导出函数） |
| 改动页面 | `views/resident/CreateOrder.vue`、`views/worker/TaskList.vue` |
| 后端 | **未改动**（`description`、`handleNote` 字段早已存在） |
| 验证 | `vite build` 通过；词库函数用 Node 跑了拼句与分组用例 |

**报修侧（住户）**

1. 选完「报修类型」，自动把该类型的第一条例句填进「详细描述」，标题为空时一并补上。
2. 描述框下方出现「常用写法」标签组（每个类型 3~4 条），点一下即可换成另一条。
3. 只在"描述为空"或"仍是上次自动填的内容"时才覆盖，**不会冲掉住户自己写的东西**；标题同理。
4. 填进去的是完整可提交的句子（含时间、影响、诉求），住户按实际改两个字就能用。

**完工侧（维修工）**

1. 「完成维修」弹窗上半部分是三组勾选：故障原因 / 处理方式 / 结果确认，选项按工单类型取。
2. 勾选后实时拼句，示例：`经检查，故障原因为水龙头阀芯老化；已更换配件、紧固接线；已通水测试无渗漏，已清理现场。`
3. 拼好的句子落在下方 textarea，可继续手写补充；也可完全不勾选，直接手写。

**设计口径**

- 分组用**类型名关键词**匹配（先判「电梯」「门禁」再判「门窗」，避免"电梯"被"电"误判到水电组），管理员改类型名只要保留关键词仍能命中。
- 词库与页面解耦：以后加类型、改文案只动 `suggest.js`，不碰 Vue 文件。
- 生成的是**可编辑文本**，不落库、不影响派单和状态流转，误填也没有副作用。
- **防覆盖**（用户实测反馈后补，最终版=撤销）：点例句直接替换，替换前若检测到内容被手改过（`!== autoFill.desc`），先把原内容存进 `undoState`/`undoNote`；文本框下方显示一行「撤销」，点一下恢复。重新手动输入（`@input`）即清空暂存。**不用弹窗**——弹确认打断操作，比直接覆盖更烦。

## 6.8 站内消息可删除（2026-10-29 下午）

原来消息只能标记已读，越攒越多。加了两种删除方式：

| 方式 | 接口 | 行为 |
|---|---|---|
| 单条删除 | `DELETE /api/messages/{id}` | 只能删自己的（越权抛"无权删除该消息"）；消息不存在时静默返回，重复点击不报错 |
| 清空已读 | `DELETE /api/messages/clear-read` | 删掉自己所有 `is_read=1` 的消息，未读保留，返回删除条数 |

前端（`MessageCenter.vue`）：

- 每条消息右侧一个垃圾桶图标，**点删除不弹确认**——消息不是业务数据，误删无所谓，弹窗反而拖慢操作；
- 头部加「清空已读」按钮（红色描边），批量操作弹一次确认；
- 删除后若当前页只剩这一条且不在第一页，自动回退一页，避免停在空白页。

**注意**：`/clear-read` 必须在 `/{id}` 之前声明。虽然 Spring 的字面量路径优先级更高，但排在前面能避免以后换成 PathPattern 解析器时踩坑。

## 6.9 移除登录锁定（2026-10-29 晚，用户决定）

**起因**：用户连错 5 次后发现提示仍是"用户名或密码错误"，怀疑锁定没生效。查库确认其实锁了（`lock_until` 已写入，正确密码也登不进），只是**第 5 次的提示被吞了**——密码校验写在锁定检查之前，密码一错就抛异常，走不到锁定判断。

修好顺序后用户问"这功能好像没什么用"，讨论后决定**整个移除**。理由：物业内部系统，被锁的基本是忘了密码的住户，而没有"忘记密码"兜底，锁了只能等或找管理员改库；对真正的猜密码攻击，5 次锁 10 分钟也只是拖几分钟。

**改了什么**

| 文件 | 改动 |
|---|---|
| `UserService` | 删 `MAX_FAIL_COUNT`/`LOCK_MINUTES`、`recordLoginFail()`、登录成功后的清零 update、锁定检查；登录简化为「查账号 → 校验密码 → 查禁用 → 发 token」 |
| `ProfileController` | 改密时不再置空失败计数与锁定时间 |
| `User` 实体 | 删 `loginFailCount`、`lockUntil` 字段 |
| `sql/init.sql` | 删 `login_fail_count`、`lock_until` 两列 |
| 数据库 | 已执行 `ALTER TABLE user DROP COLUMN login_fail_count, DROP COLUMN lock_until` |

**保留的安全措施**（论文"安全性设计"写这些）

- 密码 BCrypt 加盐存储，库里看不到明文
- 账号不存在与密码错误返回**同一句提示**，防止被用来枚举系统中存在哪些账号
- 禁用账号即使密码正确也拒绝登录
- JWT 无状态令牌 + `@PreAuthorize` 按角色拦截，越权请求返回 403

**注意**：论文里不能再写"连续失败锁定"这一条，否则与代码不符。`sql/upgrade_v2.sql` 里还留着当初 `ADD COLUMN` 的历史语句，属升级记录，不必修改。
